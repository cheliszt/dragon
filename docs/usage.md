# translator-dragon 使用手册

这个工具把一次本地文件选择变成完整流水线：

1. 检测本地 PDF 文字层，选择本地提取或提交 AI Studio PaddleOCR 异步 API；
2. 自动轮询任务并下载 JSONL，抽取 Markdown 与图片；
3. 生成带稳定块 ID 的源文工作稿；
4. 选择源语言与目标语言，批准源文后进行 AI 语言检测与句段分析，再分片翻译；
5. 运行确定性检查和独立语义质检；
6. 输出双语稿、目标语言译稿和 QA 报告。

不需要在 PaddleOCR 网页手动上传和下载，也不需要在本机部署 PaddleOCR 模型。

## 网页入口（推荐）

填写好 `.env` 后，双击项目根目录的 `start-web.cmd`，浏览器会自动打开本地工作台。
也可以在项目目录运行 `npm start`。默认地址为 `http://127.0.0.1:4318`；端口被占用时会自动换用下一个端口，并显示实际地址。

1. 点击「选择 PDF」或拖入文件，选择「自动判断」「本地提取文字」或「云端 OCR」，勾选材料包含的源语言并选择目标语言，再点击「开始处理」。“自动判断”仅指原文获取方式。
2. 识别完成后，在「原文校对」中对照 PDF 修改识别文字，保留 `block_id` 段落标识。上方的待核对清单会列出 `CHECK-SOURCE`、`TODO`、`UNCERTAIN` 标记的页码、原因和附近文字；选择条目或点击「上一处／下一处」「定位原文与 PDF」即可选中原文标记并跳转 PDF 原页。页码使用 PDF 文件页序。
   对照原页修正或确认后，点击「已核对，移除此处标记」，保留正文和定位标识；可撤销上次确认。修改尚未保存时会提示保存。所有标记处理完毕后再批准；确认疑点本身不会启动翻译。
3. 点击「保存校对」，核对语言选项，再点击「批准原文并翻译」。有未保存修改时，批准前会自动保存。
4. 在「双语审阅」「译文稿」「正文质检」中查看结果。译文稿可下载 Markdown、Word 或 PDF；Word/PDF 按当前人工修订稿即时生成，清除内部定位标记与 Markdown 排版符号，保留正文、标题及注释。双语审阅可下载独立 HTML，在浏览器中打开。

### 语言选择、保留规则与拼音

源语言可多选英语、简体中文、繁体中文、日语、韩语、汉语拼音；目标语言可选简体中文或英语。默认英语→简体中文。中文源语言选项包含汉语拼音，也可只选拼音。简繁分别判断：目标为简体中文时，原有简体中文保留，只有选中的繁体中文才转换。

提取和校对后的原文继续使用原有跨页接续、完整句边界和分组算法。翻译前，模型在每个现有单元内做一次语言检测及自然句段标注，程序逐字验证标注是否完整覆盖原文。模型结合用户选定的源语言、目标语言及标注理解和翻译各句段；不改变原有单元编号、跨页关系或分组规则。检测未知或未选语种时保留，绝不默认它们是英语。AI 检测可能误判，未知语种有待核提示。

已识别的目标语言片段及未选语种通过保护标记逐字恢复，不进行润色或改写；整个单元都应保留时不调用翻译请求。保护从既有原文整理后的翻译单元开始，PDF 排版换行、页眉及原注标记仍按原有提取整理规则处理，批准源文不被修改。检测结果按原文、所选语种及模型缓存；翻译前新增检测调用会产生 API 用量。任务开始后语言设置固定，继续任务沿用同一设置；改换语种请新建项目以保留旧稿和人工修订。

拼音依据拼写、声调、汉语上下文、原文中的汉字写法及可靠资料核实。目标为简体中文时，正文、作者脚注和文末参考文献中的汉语拼音与汉语专名罗马化均使用核实后的简体字，不附原拼音；地名记入项目专有词表，人名简称还原为对应人物的中文全名。无法确认汉字时记录具体疑点供人工核对，不编造姓名或地名。译成英语时，先理解汉语含义再译为英语，并在段后译注说明原拼音、推定含义、依据与不确定性。译文仍留有拼音时生成“拼音待人工审核”质检项，用户可编辑译文和译注、记录“已核查”或“无需修改”。后续 AI 质检和修订沿用项目语言设置。

英语目标译文的拼音译注不完整时，保存本轮译文，并把原拼音及缺项写入段后待核译注和质检项；不会因此中止、拆分重译或清空进度，也不自动猜补汉字。每组翻译保存后即更新可下载的译文工作稿和双语工作稿，无须等待全篇质检；暂停或失败时也保留已成功的拆分请求。工作稿明确标出未译范围及质检未完成状态，最终读稿另行生成。界面分别显示语言检测、译文、质检进度；语言检测完成不等于译文完成。

英语及其他非汉语专名按对应语种处理；已确认是汉语的人名、地名、机构名、文件及文献专名按前述规则还原为简体字。句子完整优先于字符预算和页码：PDF 文字层按字号及页底位置识别脚注，并逐字匹配批准原文，先分离脚注，再将下一页的正文续句接到上一段。脚注不能用其末尾句号替未完正文“通过检查”。版式证据及覆盖记录保存于 `04_qa/source-pdf-layout.json` 和版本化的翻译计划。

用户认可的历史稿可以通过经过来源校验的 `translationCheckpoint` 纳入任务：每个译文保存对应原文和来源位置的身份校验，续跑跳过已采纳单元的翻译和语言检测，仍安排后续语义质检。接续档案与批准原文、分组或目标语言不匹配时明确报错，不静默丢弃已有译文并从头开始。该接续档案不能用普通 API 缓存冒充；修改后须重新核对并纳入进度。

命令行同样支持，例如：

```powershell
node src/cli.mjs prepare "book.pdf" --source-languages zh-Hans,zh-Hant,en,pinyin --target-language en
node src/cli.mjs translate "projects\项目编号"
```

`prepare`、`ocr`、`run` 和首次 `translate` 均可使用这两个参数。`config/settings.json` 的 `translation.sourceLanguages` 与 `targetLanguage` 是命令行新项目的默认值。旧的 `sourceLanguage: auto` 已移除。内部历史路径 `06_zh/project_zh.md` 和 API 的 `kind=chinese` 保留兼容；网页英语译稿下载名为 `project_en.md`。

页面使用已有 `.env`，不会显示密钥；配置后如有改动，请重启服务。界面上的“已配置”仅表示密钥存在，不表示外部 API 已通过验证。
走本地提取的 PDF 不提交 PaddleOCR；选择 OCR 或自动检测未达标时才提交。批准后的文字会提交至 `.env` 指定的翻译服务。
网页提交后由独立后台进程处理；关闭浏览器或网页启动窗口不会终止已启动的后台任务。电脑关机或后台进程退出后，重新打开工作台会恢复尚未完成的后台任务。旧版本遗留的失败任务需先点击一次「重试翻译与质检」；已完成的有效缓存仍会复用。
历史任务保存在 `projects/`。暂停按钮会在当前请求保存后暂停；再次点击翻译即可继续。已有 OCR jobId 的识别任务可点击「继续获取原文」，不会重新上传。
本地网页仅监听 `127.0.0.1`，同一时刻处理一个任务；使用网页期间不要同时用命令行处理同一项目。

### 超时与恢复

翻译、质检分别保存进度和请求缓存，网页显示当前阶段、请求次数、接收字符数和下次重试时间。暂时断网、限流及部分服务端错误采用有上限的退避重试；密钥错误、余额不足及证书错误不会盲目重试。长时间无数据的流式响应会超时退出，未收到完成事件的部分译文不会当作成功结果。

默认每个请求最多尝试 4 次。独立后台任务最多运行 3 轮恢复，轮次间等待 60 秒、120 秒；服务要求的 `Retry-After` 更长时按该时间等待。达到上限后显示需要处理，已完成步骤保留，稍后可以手动继续。进程崩溃的自动重启也有次数限制。暂停会中止后续请求，不丢弃当前已完成响应。

这些设置位于 `config/settings.json` 的 `openai.requestAttempts`、`openai.timeoutMs`、`openai.idleTimeoutMs`、`recovery`。新项目使用较小的完整句子单元；旧项目续跑沿用已有单元，以复用缓存。重试不能解决中转站长期过载或配额不足；响应丢失后重新请求也可能产生额外 API 用量，客户端无法保证远端只计费一次。

后台状态保存在 `.runtime/task.json`，进程日志在 `.runtime/worker.log`；项目 `manifest.json` 保存阶段和请求进度。文件采用临时写入、同步、原子替换，避免进度轮询或意外退出留下半个 JSON。不要在任务运行时手动删除这些文件。

OCR 提交超时且未拿到 jobId 时，程序不会自动再提交，以免生成重复任务。请先在 AI Studio 核实提交结果。OCR 查询和下载可重试，已有 jobId 会继续查询原任务。

## 命令行准备

需要 Node.js 22.13 或更新版本。网页预览和本地提取使用 PDF.js 与本地 canvas 运行库；双击启动时会检查并安装缺失依赖，也可手动运行 `npm install`。实验样本生成使用 pdf-lib。

1. 将 `.env.example` 复制为 `.env`。
2. 在 `.env` 中填写：
   - `PADDLEOCR_ACCESS_TOKEN`：从 <https://aistudio.baidu.com/account/accessToken> 获取；
   - `OPENAI_API_KEY`：OpenAI 或兼容中转站提供的 API 密钥；
   - `OPENAI_BASE_URL`：API 基础地址；当前示例使用 `https://api.openai.com/v1`；
   - `OPENAI_MODEL`：该 API 服务可用且支持 Responses API 与 Structured Outputs 的模型名。
3. 按项目需要编辑 `config/workflow.md`、`config/style-guide.md` 和 `config/glossary.md`。
4. 运行环境检查：

```powershell
npm run doctor
```

环境检查只报告密钥是否存在，不显示密钥内容。

默认配置最终请求 `POST https://api.openai.com/v1/responses`。如果兼容服务只支持
`/v1/chat/completions`，则不能直接用于本工作流。切回 OpenAI 官方 API 时，将
`OPENAI_BASE_URL` 改为 `https://api.openai.com/v1`。

## 推荐流程

### 自动判断或本地提取

```powershell
node src/cli.mjs inspect "D:\books\example.pdf"
node src/cli.mjs prepare "D:\books\example.pdf"
node src/cli.mjs prepare "D:\books\example.pdf" --mode text
```

`inspect` 仅本地检测，不提交 API、不新建项目。`prepare` 默认自动判断：检查所有指定页，至少 85% 的页面含有 80 个以上文字或数字字符，且这些页面的异常字符比例不超过 1%，才采用直接提取。阈值在 `config/settings.json` 的 `textLayer` 中配置。

这是一项启发式判断，不保证文字层与图片内容完全一致，也不保证多栏、脚注的阅读顺序正确。仅有页码的扫描页不计为实质文字页。文字过少、疑似乱码或提取失败的页会列入 `04_qa/text-layer.json`，并在校对稿的 `pdf_page` 注释中加入 `CHECK-SOURCE`，阻止未经核对直接批准。

对照原件补录或确认这些页面后，可在网页待核对清单中逐项确认，自动删去对应注释内的 `; CHECK-SOURCE: ...`，保留 `block_id` 和 `pdf_page`。也可直接编辑工作稿，但不要删除整个段落标识。图版与图片中的文字不会由直接提取自动识别，需要人工核对或改用 OCR。

本地原文保存在 `02_source_candidates/raw_text/document.md`，之后与 OCR 共用 `reconciled/document.md`、批准快照、翻译及质检流程。本地提取不需要 PaddleOCR token；远程 URL 与图片输入仍走 OCR。`--pages` 可用于只检测并处理指定 PDF 页，例如 `--pages 29-30`。

### 1. 强制云端 OCR

```powershell
node src/cli.mjs ocr "D:\books\example.pdf"
```

默认调用 `PaddleOCR-VL-1.6`。也可以指定模型或页码：

```powershell
node src/cli.mjs ocr "D:\books\example.pdf" --model PaddleOCR-VL-1.6 --pages "1-20"
```

如果文件已经有可访问的链接，也可以直接使用 URL 模式：

```powershell
node src/cli.mjs ocr "https://example.com/books/example.pdf"
```

程序会显示新项目目录。检查：

```text
projects/<项目编号>/02_source_candidates/reconciled/document.md
```

在这里校正 OCR 错误并处理 `CHECK-SOURCE` 等标记。

### 2. 批准源文

```powershell
node src/cli.mjs approve "projects\<项目编号>"
```

批准操作会生成不可变修订快照及 SHA-256。批准快照被修改后，翻译会拒绝继续。

### 分块与跨页句子

原文块用于校对和追溯，不再直接等同于翻译单元。批准校对稿时，程序会自动生成连续原文：逐一比较相邻内容块的结尾与开头，略过页码标记和可识别的重复页眉，将续句和排版断词接好，再沿句末划分翻译单元。PDF 页码、空白页和长度限制不构成正文分句边界；正文中的换行年份（例如 `2021.`）不会把整页误判成编号列表。`ner- / vous` 会接成 `nervous`；原文中可确认的复合词连字符（如 `self-aware`）保留。

连续原文、来源映射和逐边界检查记录保存在 `03_source_approved/<修订号>/translation-inputs/<版本>/` 中的 `document.md`、`translation-plan.json` 和 `boundary-audit.json`。批准快照本身不变；网页在批准后展示连续原文。正文翻译单元必须以完整句末结束。标题、目录、表格、代码、书目及引文署名按结构保留，不强行添加标点。若原文确实缺失、无法接续，程序记录残句并停止提交，不能靠补写内容通过检查。

学位论文的短题名页（含提交学位说明）、信件落款按结构保留。连续页序可验证的罗马数字页码不会截断跨页正文。页末出现至少两条连续、可对应本页正文注号的引文注释时，程序将其保留为独立注释单元，并接续下一页的正文；不会把脚注文字塞进正文句子。结构判断及注释段落对应关系记录在 `boundary-audit.json` 的 `layoutClassifications` 中。仅有一个无依据的编号或真实缺失后文，不能靠这些规则通过检查。

`chunkMaxChars` 是软上限：单个完整长句可以超限，不能为凑字数截断；超时后只拆分单元之间的请求批次，不再拆开单元内部的句子。分句使用标点、缩写及结构规则，遇到真实缺文、异常标点或识别不出的版式仍需人工核对，不会凭空补写。

既有项目的工作规程快照可能仍包含旧的逐块限制；运行时的新规则明确以翻译单元为准，无需改动批准原文。新旧分组使用隔离的缓存。重试时，只复用源文、来源位置、模型、目标语言与工作规程一致的完整单元；改变边界的内容重新翻译，连同邻近内容重新质检，不拼接旧的残句译文。迁移前的译稿及质检报告备份到旧运行目录的 `publication-before-boundary-repair/`。升级代码本身不会自动改写已完成译稿；在网页点击「重试翻译与质检」时使用新逻辑，并产生相应 API 用量。

第 8 版分组会接合参考文献条目中的续行和跨页内容，保留下一条作者署名、题名及小标题的边界；完整书目和脚注不因长度限制而切碎。附录独立分类，节目表行、剧本人物换段和中文列项仍保留边界。审阅界面不会再次按中英文句数拆分已规划的单元。


可先进行不调用 API 的分组预演，结果写入项目的 `04_qa/translation-plan-preview.json`：

```powershell
node scripts/plan-translation.mjs "projects\<项目编号>"
```

重译和质检完成后，可运行 `node scripts/verify-boundaries.mjs "projects/<项目编号>"`，核对原文覆盖、句末边界、译文单元和最终阅读稿，结果写入 `04_qa/boundary-repair-verification.json`。该检查不调用外部 API，也不等于学术译文的语义质检通过。

### 3. 翻译和质检

```powershell
node src/cli.mjs translate "projects\<项目编号>"
```

最终文件位于：

```text
05_bilingual/project_bilingual.md
05_bilingual/project_bilingual.html
06_zh/project_zh.md
04_qa/final.md
```

中文稿去除内部锚点、定位注释及重复页眉，合并普通段落中的 PDF 硬换行；保留空行分段、目录、列表、表格等结构。原文工作稿和批准快照继续保留定位标识。

双语 HTML 依次呈现原文段落、中文段落及疑点说明与建议。能逐字匹配的疑词以黄色高亮；无法精确定位的旧报告问题以浅色标注整段，不推测问题位置。可以查看前后文、关联段落及 PDF 原页。分段以现有文本为依据，不保证还原 PDF 的所有自然段。

「正文质检」默认只显示正文、目录、注释和参考文献中的待核问题；版权、致谢及排版记录另列为辅助内容，可手动调整归类。网页中的判断和备注保存到项目的 `04_qa/review-decisions.json`，多窗口覆盖或版本不符时会拒绝保存。独立 HTML 的判断保存在当前浏览器中，可下载 JSON 留存；不会自动同步到项目。移动 HTML 后，原 PDF 的相对链接可能失效。

在「正文质检」或「双语审阅」中，可以用以下方式修订：

- **保存意见**：保存备注并显示反馈，本身不改动译文。
- **AI 按建议修订**：根据该项质检建议和填写的意见生成本段草稿；意见可留空。AI 使用 `.env` 配置的服务和模型，会产生相应 API 用量。可比较修改前译文、继续编辑草稿，再点击「应用修订」。
- **编辑译文**：直接修改中文段落，点击「应用修订」保存。未应用草稿暂存在当前浏览器，刷新后可继续编辑。
- **前后文**：展开后，上段和下段也有相同的编辑框与修订历史；即使邻段不在当前问题筛选结果中，也可以直接修改，保存后正文及下载稿同步更新。
- **修订历史**：查看每次修改前后文字，并将历史译文放回草稿后恢复。

应用后，网页中文稿、双语稿及下载文件同步使用修订版本；原始译文缓存不变。修订记录和完整导出快照存放在 `07_revisions/<读稿版本哈希>/<修订编号>/`，该版本的 `current.json` 指向最新修订。上面列出的 `05_bilingual`、`06_zh` 文件保留原始机器译稿；需要最新修订稿时从网页下载或按 `current.json` 的 `outputs` 路径读取。重复生成相同读稿不会丢失修订；重新翻译导致读稿版本变化时，旧修订单独保留，页面会提示，不能按旧段落编号直接套用。

AI 草稿由独立后台进程生成，刷新网页或重启网页服务后仍可读取。生成失败或进程中断会显示原因，不会自动改写译文或无限重试。翻译、质检和 AI 修订共用并发锁；整书任务运行时需等待或先暂停。多窗口修改同一稿件、或 AI 草稿对应的译文已变化时，系统拒绝覆盖并保留浏览器草稿。

新导出的独立 HTML 可直接编辑译文并下载修订中文稿，但仅保存在浏览器，不会写回项目，也不能直接调用 AI。网页中的「应用修订」不会自动清除机器质检疑点，仍需核对后选择「已核查」或「无需修改」。`qa_failed` 表示译稿已生成、仍有质检问题待处理，不等于 API 翻译失败。

已有完整翻译缓存的项目可离线重新生成阅读稿，不调用外部 API：

```powershell
node scripts/rebuild-reading.mjs "projects\<项目编号>"
```

### 一次运行到底

```powershell
node src/cli.mjs run "D:\books\example.pdf" --auto-approve
```

这会跳过人工源文批准，适合测试，不推荐直接用于正式学术交付。

## AI Studio 限制

官方异步 API 当前说明：

- 本地文件上传最大 50 MB；
- 文件链接模式最大 200 MB；
- 单次最多 1000 页 PDF；
- 服务返回异步任务 ID，完成后提供 JSONL 结果地址；如果同时提供 Markdown 地址，工具仍会优先使用 JSONL 中的 `layoutParsingResults[].markdown.text`；
- 任务可能因配额、请求频率或队列已满而失败。

本工具会保存任务响应和进度；OCR 查询与下载遇到 429 或服务器错误会有限次退避重试。OCR 新任务提交只尝试一次。超过 50 MB 的本地文件应先拆分，当前版本不会擅自上传到其他云存储。

400、401、403 等永久性错误不会自动重试。HTTP 错误详情保存到 `04_qa/ocr-error.json` 或 `04_qa/translation-error.json`，不记录认证请求头。直接运行 `node src/cli.mjs translate` 仍是前台命令，关闭该终端会中断进程；长任务推荐使用网页后台方式。

## 排查实验

### 原文自动清理

提取和翻译前分别自动运行清理检查。PDF 文字层结合边缘位置与跨页重复识别页眉、页脚和边栏；OCR 的逐页结果保留页位置，供第二次检查使用。作者注号与排版页码分开处理：小号字的上标位置、明确的上标语法或连续注号序列可作为证据，将 `sentence.16` 整理为 `sentence.[^16]`，不会把 16 当成句子中的数值。孤立到下一页开头的已确认注号仍归属前一句。翻译保留对应的 `[16]` 原注关联，读稿中由注释系统呈现为上标与原注内容。

年份、数量、小数、公式、列表、参考文献及注释正文保留。证据不足的数字留在原文并写入自动检查记录，不会要求用户逐个清除。图片上的编号不会仅因连续递增就当作页码删除。程序区分“删除排版杂质”和“规范原注标记”，两类记录分别保存在 `removals` 与 `normalizations` 中。

提取前的文字保存在 `02_source_candidates/raw_text/document.md` 或 `raw_ocr/`；清理明细在 `04_qa/source-cleanup-extraction.json`。翻译和整书质检共享清理后的连续原文，第二次清理明细在对应 `translation-inputs/<版本>/source-cleanup.json`，包含页码、原始块、删除位置、前后文和原因。批准快照不变，清理规则改变会产生新的翻译计划版本，不会误用旧缓存。

翻译、正文质检、AI 段落修订三个请求入口还会再次检查原文，适用于旧项目。旧读稿只在请求副本中规范注号，AI 的原文引句会映射回存档文字，保持网页定位有效。数值质检区分原注标记与正文数量，丢失原注关联会单独报告。中文人工修改、段落编号和原有注释定位不变，旧质检结论继续保留。已生成的中文稿和历史下载文件不会被静默重写。重新翻译会生成新读稿版本，旧人工修订按版本归档。

可离线检查现有批准稿并更新网页的连续原文，不调用 OCR 或翻译 API，也不覆盖已有译文：

```powershell
node scripts/clean-source.mjs "projects\<项目编号>"
```

已有 PDF 读稿可用 `node scripts/verify-source-cleanup.mjs "projects\<项目编号>"` 离线复核：重新提取并检查清理幂等性、全文覆盖、完整句边界及人工译文是否保持不变，结果写入 `04_qa/source-cleanup-verification/`，不调用收费 API。

### 段后原注与译注

正文下方按自然段展示对应的作者原注及中文注译。尾注按章节和注号匹配，避免不同章节从1重新编号时串注。支持编号尾注、Markdown脚注及具有可辨识版面信息的PDF页脚注。无法确定的对应关系保留待核记录，不虚构注释来源。

- “编辑原注”可以校订作者原注的原文和中文译文；原始注释文本仍保存在注释目录中。
- “＋ 译注”打开独立编辑框，可为该自然段新增、修改或删除译者说明；译注始终标为“译注”，不混作作者原注。
- “整理段后注释”可为已有项目补建关联，或在正文修订后更新位置。缺失的注译和定位使用当前配置的翻译API，有独立缓存和后台进度。
- 注号恢复通过可核验的中文原句位置实现；定位请求只返回原样引文，不能修改正文。正文修改造成定位引文失效时，保留注释并等待重新整理。
- 网页下载的中文稿、双语稿和独立HTML包含段后注释。独立HTML的修改只保存到浏览器，可另行下载修订中文稿。

注释目录、定位证据、原注修订和译注保存在 `08_annotations/<读稿版本>/`，与正文的 `07_revisions/` 分开。注释保存有版本和修订冲突检查，不会覆盖其他窗口的修改。

命令行整理已有书稿：

```powershell
node scripts/prepare-annotations.mjs "projects\<项目编号>"
```

整理后可运行离线验收，核对正文与人工修订哈希、全部注译、注号所属自然段及导出文件的一致性。结果写入注释目录的 `verification.json`；未完成定位或正文在整理后又被修改时，会明确报错。

```powershell
node scripts/verify-annotations.mjs "projects\<项目编号>"
```

### 全稿编辑、术语检索与修订稿质检

“双语审阅”默认展示全部书稿，包括没有 AI 疑点的段落。每段均可直接编辑译文、查看修订历史、添加译注；这个视图不按问题级别筛选。“正文质检”单独展示 AI 核查意见及修改后待重检的段落。

两处读取同一份最新人工主稿。人工保存后，旧质检会标明“历史意见”和所依据的修订版本，旧高亮不会套用到新文字。可选择“重新质检本段”“质检已修改段落”或“质检全稿”；这些操作调用配置的 API 并消耗额度，只生成核查意见，绝不自动覆盖译文。质检和 AI 草稿生成期间仍可人工编辑；期间产生的新修改会使旧快照的结果失效。AI 草稿只有经用户应用才成为主稿，过期草稿拒绝覆盖新译文。

“搜索字段”可选择原文、中文译文、原注与译注或全部；搜索按字面匹配，不执行正则表达式。默认也能找到词中的匹配部分，例如 `coworker` 能找到 `coworkers`；可勾选整词匹配。命中列表列出每次出现的页码及上下文，可逐处跳转、高亮和修改，不进行一键强制统一替换。人工修订与注释草稿独立暂存；另一个窗口有更新时，同步仍保留草稿并检查冲突。

上传原文和正式翻译前会识别独立的 Glossary、Glossary of Concepts、术语表或名词解释等部分，保存原文释义、页码和来源块到 `00_shared/author-terminology.json`。翻译、修订和重新质检都会参考这些作者定义，词条无法可靠拆分时保留整个释义部分供参考。没有识别到独立部分时，不虚构作者定义。全文检索还会展示匹配的作者释义。

中文翻译优先为容易误解的特殊用语采用引号，并在一种译法首次出现时括注原词；同一源词因语境而采用不同译法是允许的。例如“黑人性”和“黑性”可分别在首次出现时标注 `blackness`，并用独立译注说明译者的语义判断，而不把这种判断混作作者原话。新的规则会进入请求缓存身份，不沿用缺少作者释义依据的旧请求缓存。

修订稿质检的快照、结果和历史记录保存于 `04_qa/revisions/<读稿版本哈希>/`。初次质检报告继续保留，当前稿的核查状态由最新正文与质检快照共同决定。网页下载稿始终从当前人工主稿生成。

`scripts/diagnose.mjs prepare` 只生成本地样本；`probe-ocr` 和 `probe-translation` 会实际调用 `.env` 指定的服务并可能消耗额度。

## REST API 与 MCP 的选择

AI Studio 同时提供 REST API 和 PaddleOCR MCP。固定的批量翻译流程优先使用 REST API，因为任务状态、文件版本、失败恢复和审计记录都更明确。MCP 更适合在交互式大模型客户端里临时请求 OCR；它仍需要安装并运行 `paddleocr-mcp` 客户端，但推理可以使用 AI Studio 云端服务。

## 安全与学术使用

- `.env` 已被排除，不应提交或分享。
- 云端 OCR 会将原始文档发送给百度 AI Studio；本地文字提取不发送原始文档。翻译、质检与 AI 修订会将相应文本发送给 `.env` 配置的 API 服务。
- 上传受版权、保密或个人信息约束的材料前，应确认相应的数据处理条件。
- GPT 质检不能替代原页核验。正式成果应保留批准源文、OCR JSONL、版本哈希和人工审核记录。
